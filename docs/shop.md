# 商城与快速挑战（2026-11-12）

首页右侧排行榜下方为「商城」。三张商品卡沿用奶油底、暖色描边与软糖按钮，鼠尾草绿、雾蓝和浅杏色分别区分解压锤、魔法棒和体力；道具按原贴图比例显示。标题、蓝灰色一句话效果描述、持有数量上下留空。按钮统一显示居中的开心豆图标及「兑换 [持有豆数/价格]」，图标为原来80%；价格绿色，余额随是否足够显示红/绿。按压缩小，松手恢复。

解压锤、魔法棒各20豆兑换1个；体力5豆兑换1点；体力图标为暖金色圆角闪电，完整笑脸位于中腰内，首页/商城/开局飞行共用。体力支持超过自然恢复上限，未满时兑换保留已积累的恢复时间。点击不足余额的兑换按钮不会发送扣款请求，会打开「开心豆不足」提示，可返回商城或快速开始挑战。快速挑战复用首页的服务端开局流程，体力不足时进入原补充体力弹窗；同一时间仅允许一次开局请求。首页开始按钮和快速挑战按钮上方都有每秒刷新的体力/恢复倒计时。

## 资产与操作

- `POST /shop/exchanges`：`actionId`、`item`（`hammer` / `magicWand` / `stamina`）；服务端商品表固定20/20/5豆扣款、增加1件/1点体力，同事务持久化。忽略客户端价格与数量。余额不足不产生流水；同 ID 不同商品返回冲突。相同请求重试返回当前档案，不重复扣款。
- 客户端兑换前持久化 ID；结果不明保留请求并显示「继续确认」，确认前不发第二笔兑换。并发点击由界面与接口双层处理。关闭弹窗不取消已经发送的请求。
- `POST /games/tools/use`：当前 `roundId`、动作位置 `actionIndex`、道具与目标。服务端立即扣一件并记录凭据，客户端得到确认才改棋盘；网络结果不明冻结该动作，重试复用 ID 和目标。新局结算按操作位置、类型、目标逐条检查道具凭据，不能靠修改本地库存免费使用。
- `POST /games/tools/reward`：沿用已有分享/广告完成回调，每局每种最多三次补给，领奖 ID 幂等。补给和商城道具共用服务端库存；次数上限在道具说明中写明。该回调目前仍属于客户端完成声明，**不等于接入广告平台服务端验签**，不能宣称已阻止伪造广告完成。后续若需真实广告收益，应补平台验证。
- 所有玩家写入推进 `assetRevision`。客户端忽略低版本及迁移前无版本的历史回执，防止旧结算余额覆盖消费、旧库存覆盖使用；开局返回最新权威档案，刷新不会补回已用道具。
- schema v8 原地增加 `hammer_count` / `wand_count` / `asset_revision`、`tool_transactions`，不重算原余额。历史本地道具不是可信建档来源，不自动上传；服务端初始库存为零。GM 专用工具同步现已包含道具，生产仍禁用 GM 路由。
- `game_rounds.tool_rules_version`：历史在途局为 0，新局为 1，只对新局强制使用凭据，避免旧补传因新增协议被拒绝。默认关闭旧协议新开局，防止直接报数领取旧制奖励；`ALLOW_LEGACY_ROUND_STARTS=1` 仅供历史兼容回归夹具，正式环境不配置。

## 复核修复与验证

复核修复了本地库存与云档案不一致、旧结算快照回滚资产、重复兑换与未知结果重试、禁止按钮仍会触发点击，以及首页加载提示覆盖结算标题的问题。范围内验证不能替代完整反作弊审计；生成合法操作的自动化玩家、救场授权及广告平台验签不属于商城扣款的事务保证。

`server/test/shop.test.js` 覆盖价格/数量篡改、双击/并发透支、幂等冲突、落盘故障、库存刷新、实际工具重放和补给次数；模块测试覆盖乱序及无版本回执。`scripts/verify-shop.cjs` 使用独立临时数据库和真实 API，验证实际界面点击、响应丢失重试、两种道具使用和结算、不同屏幕截图，不修改玩家存档或访问外网。产物在 `output/shop-verification/`。
