### 玩家资料与授权

### 体力规则

- 自然恢复上限由 30 改为 **10**，恢复间隔由 10 分钟改为 **5 分钟 1 点**，每局仍消耗 1 点。

- 高于或等于上限时没有恢复倒计时；低于上限后从服务端恢复基准继续计时。
- 分享仍可每天领取 5 点，满体力时也可领取，例如 10＋5＝15；同一 `claimId` 保持幂等。
- 新账号显式写入 10 点初始体力，兼容历史数据库列默认值仍为 30 的情况；旧账号已有超额体力保留。
- 主页体力胶囊下方显示 `mm:ss 后恢复`，服务端时间仍是唯一权威。
- 关键文件：`server/src/economyConfig.js`、`server/src/schema.js`、`server/src/index.js`、`assets/script/GameMainScene.ts`。

- 服务端删除 `weekly_stats` 及相关索引、周计算、结算周写入和 `currentWeekId`；`schema.js` 当前 `user_version = 3`。
- 排行榜响应保持 `{ entries, self: { rank, bestScore, onBoard } }`，不要恢复旧 `weekId/type/periodStartAt/isRanked/distanceToRank200` 协议。
- 关键文件：`server/src/index.js`、`server/src/schema.js`、`server/src/databaseAudit.js`、`assets/script/manager/CloudService.ts`、`assets/script/zyxGame/LeaderboardPanel.ts`。

### Production / Staging 双环境

- `assets/script/manager/CloudService.ts` 固定路由：微信 `release` → Production；微信 `develop/trial` 和 Web 预览 → Staging。
- 测试统一使用 `https://staging-api.tcjstory.cn/v1/cocos-zyx`；只有明确发布 Production 时才切换正式数据。
- Staging 使用独立 Compose 项目、容器、数据卷和 `.env.staging`，不得删除或复用 Production 数据。
- 服务器 Caddy 子域转发按主机名区分；共享网关检查只验证 Dawn、Chloe 等既有服务，不阻止不同主机名转发。
- 测试模式 401 时使用原请求参数重新 bootstrap 并重试一次，保留 `roundId` 和请求体。

### 服务端种子重放校验

- 开局由服务端生成并保存 `seed`、`is_tutorial`，连同 `roundId` 返回客户端。
- 客户端记录本局操作序列，结算时随 `actions` 提交；服务端用 `server/src/gameEngine.js` 重放并校验分数与开心豆。
- 非法操作返回 `REPLAY_INVALID`，提交值与重放结果不一致返回 `REPLAY_MISMATCH`。
- `game_rounds` 已有 `seed/is_tutorial` 字段；不要退回只信客户端分数的结算方式。

### 消除表现与资源回收

- 消除淡出、行闪光、扫光和碎片动画由逐帧重绘 Graphics 改为创建时绘制一次，tween 直接驱动节点属性。
- 碎片使用有上限的对象池；`cc.tween(node).stop()` 的误用统一替换为 `cc.Tween.stopAllByTarget(node)`。
- `ZyxGame.onDestroy` 统一取消延迟回调、停止根节点动画并销毁池内碎片；异步回调保留 `cc.isValid` 守卫。
- 不要恢复每帧重建碎片顶点的旧实现。

### 验证状态

- 永久榜和重放相关前后端测试、Web/微信构建已通过。
- 上述改动随后包含在 2026-11-02 的 Staging 与微信候选包中；Production 是否发布必须以单独发布记录为准，不能由本地代码状态推断。

- 服务端权威管理体力、开心豆、等级、经验和最高分；客户端不得通过 bootstrap 或 GM 请求直接改写 Production 资产。

- 完成修改后至少运行 `npm test`；微信交付前运行 `npm run build:wechat`，并如实记录测试、构建、部署和真机验收状态。
