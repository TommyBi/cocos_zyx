# 复活卡：商城、玩法与服务端核验

2026-11-17完成本地实现。客户端候选 `v2026.11.16.04`，棋盘规则V11，API15，数据库结构10；不更改玩家数据代际。采用用户认可的第二次生成结果：运行图 `assets/bundles/effects/images/formal/revive_card_v2.png` 与审批归档 `docs/ui-concepts/revival-card-20261116/revival-card-candidate-v1.png` 字节一致，未重绘。

## 玩家流程

| 情况 | 行为 |
| --- | --- |
| 商城购买 | 25开心豆兑换1张复活卡，放入背包；其余商品仍为3豆 |
| 每局第一次失败 | 保留现有广告/分享复活入口；拒绝则结算，不消耗卡 |
| 首次复活后再次失败，库存大于0 | 提示使用1张复活卡或本局结算，绿色使用按钮在右 |
| 首次复活后再次失败，没有卡 | 直接结算，不弹购买或用卡提示 |
| 本局已用卡后再次失败 | 直接结算，即使背包还有卡也不能再用 |
| 用卡请求结果未确认 | 冻结该动作，提示重新确认，不重复扣卡 |

复活卡清理顶部8排，按现有补排及稳定消除规则继续。商城改为裁切的纵向滑动列表，保持原商品卡尺寸及留白，第四张卡可滑动查看；显示卡片图标、库存“张”和25豆价格。兑换成功弹窗使用同一获批图标。资源保存在effects分包，避免增加主包贴图。

## 服务端与资产

- schema10原地增加 `players.revive_card_count INTEGER NOT NULL DEFAULT 0`；旧余额、等级、经验、库存、分数、对局及结算不变。重复迁移保留已有卡片。库存跟随 `assetRevision` 返回，客户端持久化并拒绝低版本回执。
- `POST /shop/exchanges` 新增 `item: reviveCard`，服务端固定25豆换1张。忽略客户端价格和数量，复用现有交易ID、原子扣款发货、可靠落盘与未知结果重试；不开放广告免费领取卡片或通用工具接口直接扣卡。
- `POST /games/revive-card` 接收本局 `roundId / sessionToken / actions / elapsedMs`，仅支持V11保存协议对局。校验本人、有效未结算对局、当前会话、不可改写前缀、时间、种子重放、首次复活记录、再次失败和库存。
- 服务端从日志重建失败棋盘，生成 `reviveCard` 动作及后续稳定消除、补排、完整操作结束记录。同一事务写入扣1张库存、资产版本、使用凭据和完整恢复进度，可靠落盘后才返回。使用凭据记录动作位置和固定8排目标。
- 同局卡片请求按原前缀长度和内容幂等确认；并发请求只有一次扣卡。客户端未知结果保留原请求重试。扣卡成功但动画前退出/丢响应，云端已保存完整复活棋盘，恢复不会回到用卡前。
- 保存与最终结算逐条核对 `reviveCard` 使用凭据，并重放V11顺序/次数/失败状态及8排范围。不能用第二次广告复活替代用卡，也不能伪造卡片动作、移除已确认用卡前缀或跨账号/旧会话结算。
- 新版保留V10保存局恢复、一次复活及结算；不把旧局升级成额外复活。后端继续兼容V5–V10新开局和旧版结算。上线顺序为API15/结构10后端，然后新版客户端；客户端开局检查 `revive-card-v11` 能力。
