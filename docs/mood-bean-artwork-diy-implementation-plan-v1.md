## 1. 改造结论

本轮改造把现有链路：

```text
消除带表情的心情块
→ 表情进入开心瓶
→ 每 66 个表情形成 1 枚开心瓶
→ 消耗开心瓶打开画册和点亮画作
```

改成：

```text
消除带表情的心情块
→ 每个带表情的心情块直接显现为 1 颗同色、同表情的“心情豆”
→ 心情豆直接投入时空秘境中的官方拼画
→ 拼满画作后熨烫定型，解锁高清原画

或：

心情豆
→ 在“心情调色铺”按 10:1 调成指定颜色的“彩豆”
→ 在“心情画板”免费设计草稿
→ 定型时消耗彩豆，形成个人 DIY 作品
```

核心原则：

1. 不再存在“表情先转化为瓶子，再把瓶子当货币”的二次语义跳转。
2. 心情豆是消除玩法直接产出的通用创作材料；一个带表情心情块固定对应一颗心情豆，不是金币、钻石、瓶子或二次换算货币。
3. 官方画作使用心情豆；DIY 作品使用彩豆，两者用途明确。
4. 所有数值集中配置，第一版先验证闭环，不在代码中散落魔法数字。
5. 先清空旧数据并建立新服务端权威，再替换界面和动画。
6. 第一版不做公共 UGC 广场、点赞、评论、图片导入和作品交易。

## 2. 两个独立交付阶段

本方案拆成两条可以独立验收的成长线。任何执行模型必须先确认当前被授权的是阶段 A 还是阶段 B。

### 2.1 阶段 A：主线官方拼画（优先实施）

- 用“心情豆”完整替代开心瓶的收集、余额和消费语义。
- 保留经验、等级、最高分和消除核心玩法本身；已有玩家数值仍随数据重置归零。
- 将现有 750×1000 官方画作改造为 650×780 运行素材。
- 每册画作拥有独立画框视觉；画框与原画资源分离并按册复用。
- 官方画作改为 130×156、共 20,280 个逻辑豆位的拼画进度。
- 玩家能够把心情豆投入当前画作，看到连续拼豆动画和明确进度。
- 画作完成时播放“熨烫定型/融合成画”，显示高清原画。
- 本地和服务端旧用户数据被完整清空，新版本从空档开始。
- 新增主线所需的客户端单测、服务端集成测试、资源校验和手工验收。

阶段 A 完成后，产品必须可以在完全没有调色铺、彩豆和 DIY 画板的情况下独立运行和发布。

### 2.2 阶段 B：调色与 DIY 创作（等待再次布置）

只有阶段 A 已完成验收，并且用户再次明确下达开发任务后才能开始：

- 增加心情调色铺，暂按 10 颗心情豆兑换 1 颗指定基础彩豆；
- 增加 8×8、16×16、32×32 DIY 画板；
- DIY 在草稿阶段不消耗材料，定型时一次性扣除彩豆；
- 增加私有作品保存和展示；
- 作为增量功能保留阶段 A 已产生的心情豆、官方画作和其他新档数据；
- 阶段 B 不再次执行本地或服务端数据清空。

### 2.3 两阶段都明确不做

- 不做 64×64 或更大 DIY 画板。
- 不做用户上传图片自动转拼豆。
- 不做公共作品广场、搜索、点赞、评论、关注和排行榜。
- 不做玩家之间赠送、售卖或交换彩豆。
- 不做动画彩豆、透明豆、金属豆等特殊材料经济；只预留 `colorId` 扩展空间。
- 不做复杂的局外生产队列、等待时间和加速系统。
- 不重新设计消除棋盘规则、重力、道具或复活流程。
- 不顺手重构现有 UIManager、AssetLoader 或服务端框架。
- 不做任何旧客户端、旧存档或旧数据库字段兼容。

### 2.4 强制停止线

阶段 A 的执行模型不得：

- 新增 `color_bean_inventory` 或 `diy_works` 表；
- 新增调色铺、彩豆库存、DIY 草稿或作品入口；
- 在首页放置不可用的 DIY 占位按钮；
- 以“为后续扩展”为由预建通用创作框架；
- 执行本文阶段 B 的任何任务。

完成阶段 A 后提交验收结果并停止，等待用户另行布置阶段 B。

### 4.1 对玩家使用的名称

| 概念 | 正式名称 | 说明 |
|---|---|---|
| 消除中收集的通用材料 | 心情豆 | 每个带表情心情块消除后直接产生 1 颗；可用于官方拼画或调成彩豆 |
| DIY 中的具体颜色材料 | 彩豆 | 具有明确 `colorId`，定型 DIY 作品时消耗 |
| 官方画作入口 | 时空秘境 | 保留现有入口和世界观 |

- “消除带表情的心情块，收集心情豆”

- 开心瓶

## 5. 两阶段参数基线

所有可调数值必须集中在一个客户端配置文件和一个服务端权威配置区，禁止散落在 UI 代码里。

### 5.1 阶段 A 固定结构参数

| 参数 | 值 |
|---|---:|
| 设计分辨率 | 750×1334 |
| 官方原画运行尺寸 | 650×780 |
| 官方拼画单格尺寸 | 5×5 设计像素 |
| 单格内部结构 | 1 像素格线/间隙 + 4×4 有效色块 |
| 官方拼画列数 | 130 |
| 官方拼画行数 | 156 |
| 官方拼画总豆位 | 20,280 |
| 推荐画框外尺寸 | 不超过 700×830 |

### 5.2 阶段 A 暂定经济参数

| 参数 | 暂定值 | 备注 |
|---|---:|---|
| 每个带表情心情块对应心情豆 | 1 | 固定语义，不作为经济调节项 |
| 单次默认投入官方拼画 | 500 | 余额或剩余豆位不足时取较小值 |
| 单次最大服务端拼画投入 | 5,000 | 防止异常请求；“全部投入”需要拆成合法事务或由服务端裁剪 |
| 首册开放等级 | 1 | 第一册免费进入，不额外扣豆 |
| 第二册开放等级 | 5 | 暂定；后续按实际等级节奏调整 |

### 5.3 阶段 B 参数（暂定，阶段 A 不实现）

| 参数 | 暂定值 |
|---|---:|
| DIY 画板尺寸 | 8×8、16×16、32×32 |
| 基础彩豆颜色数 | 12 |
| 心情豆兑换基础彩豆 | 10:1 |
| 单次最大调色数量 | 1,000 颗 |

### 5.4 数值关系

650×780、5×5 一格时：

```text
650 / 5 = 130 列
780 / 5 = 156 行
130 × 156 = 20,280 个豆位
20,280 / 500 ≈ 40.56 局
```

如果希望一幅标准画作约 60 局完成，平均每局需要实际收集约 338 个带表情心情块。只能通过心情块出现率、单局长度、画作豆位数或独立结算奖励调节节奏，不能把一颗局内心情豆解释成 10、50 颗余额。

核心规则始终保持：

```text
1 颗投入官方画作的心情豆 = 1 个官方画作豆位
```

DIY 的兑换规则则是：

```text
10 颗心情豆 = 1 颗指定基础彩豆
1 颗彩豆 = DIY 画板中的 1 个有效像素
```

## 6. 消除与心情豆发放

### 6.1 保留两个独立计数

现有 `roundCollectedMoods` 不应直接改成长期心情豆余额。新结算必须分开记录：

```text
roundCollectedMoodBeans：本局实际消除并收集了多少个带表情心情块
roundBonusMoodBeans：经服务端验证的结算额外奖励，未触发时为 0
roundEarnedMoodBeans：本局最终入账的心情豆总数
gainedExperience：本局获得多少经验
```

第一版规则：

```text
baseMoodBeans = roundCollectedMoodBeans
roundEarnedMoodBeans = baseMoodBeans + roundBonusMoodBeans
gainedExperience = roundCollectedMoodBeans
```

其中 `roundBonusMoodBeans` 必须在结算中单列展示，不能伪装成某颗局内豆子的倍率。后续调整经验曲线时也应使用独立配置，不能改变“一块一豆”的资源语义。

### 6.2 表现规则

- 带表情心情块消除时，原有贝塞尔飞行路径可以保留，但飞行物必须换成正式心情豆。
- 飞行目标从玻璃瓶改为顶部“心情豆”资源位。
- 每颗豆继承来源心情块的颜色和表情；到达后只显示 `+1`，本局数量增加 1。
- 一次消除多个带表情心情块时，每块对应一颗可见豆，并按到达顺序逐颗计数。
- HUD 显示本局累计心情豆，不显示“距离装满一瓶还差多少”。
- 经验依然在结算时独立飞向经验条。

### 6.3 结算规则

结算面板至少显示：

- 本局得分；
- 基础收集心情豆数；
- 结算额外奖励数（存在时单列）；
- 最终入账心情豆数；
- 获得经验数。

即使第一版经验恰好与基础心情豆相等，心情豆和经验也不能共用同一个 UI 数字，以免后续调整等级曲线时玩家误解。

### 6.4 广告奖励边界

现有广告/分享道具、复活逻辑保持不变。本轮只允许一个与心情豆直接相关的广告奖励：

- 结算时可选择“本局心情豆加成”，具体倍率后续测试；
- 服务端结算请求必须明确区分基础心情豆和广告加成，并保留广告结果校验扩展位；
- 第一版如真实广告链路尚未恢复，不得伪造服务端已验证广告的安全语义。

## 7. 首页与局内 UI 改造

### 7.1 首页

移除：

- 中央正在装满的开心瓶；
- 开心瓶水位、瓶盖打嗝、满瓶飞向库存；
- 右上或档案卡中的开心瓶数量名称。

替换为：

- “心情豆”资产卡：彩色豆粒图标 + 当前余额；
- 首页演示继续表现“移动—落下—消除—表情飞出”，但终点改为心情豆收纳位；
- 时空秘境入口显示当前正在拼的画作缩略图和进度；
- 阶段 A 不出现心情画板和调色铺入口；
- 阶段 B 再决定把心情画板放在首页还是秘境内部，调色铺应作为画板内的子入口。

### 7.2 局内 HUD

- 顶部保留分数、暂停和收集资源的三段结构。
- 原瓶子 HUD 改成“心情豆图标 + 本局数量”。
- 不显示总余额，避免局内同时出现本局数和长期余额造成混淆。
- 单颗心情豆到达后，本局心情豆数字增加 1。

### 7.3 结算回首页

- 心情豆从结算面板飞向首页资产卡。
- 经验飞向经验条。
- 不再播放满瓶转换动画。
- 云端结算成功后以服务端余额为最终显示；失败时显示本地待同步状态，不静默丢失。

### 7.4 排行榜

现有 `happiness` 排行类型可以暂时保留接口枚举以减少改动，但玩家文案改为：

- “本周心情豆”
- 排名值使用本周获得的心情豆数量，而不是完成瓶数。

版本切换时周榜全部清空，从新经济上线时间重新累计本周心情豆，不折算旧瓶排行。

## 8. 时空秘境官方拼画

### 8.1 画册开放规则

- 不再消耗心情豆打开整册画册。
- 画册按玩家等级开放：第一册默认开放，第二册暂定 5 级。
- 册内画作继续按顺序制作，前一幅未完成时不能投入后一幅。
- 所有玩家从第一册第一幅、0 个豆位开始，不继承旧画册或画作状态。

### 8.2 单幅画作状态

每幅官方画作只需要以下持久化状态：

```text
artId
filledCells：0..20,280
completedAt：未完成时为空
updatedAt
```

不为每幅画保存 20,280 个布尔值。第一版使用确定性填充顺序，因此 `filledCells` 一个整数足以恢复画面。

### 8.3 确定性填充顺序

每幅画配置一个焦点：

```text
focusX：0..1
focusY：0..1
revealSeed：稳定整数
```

客户端根据焦点距离和稳定随机扰动计算固定填充顺序：

1. 主体焦点附近优先；
2. 逐步向外扩展；
3. 同距离格子由 `revealSeed` 决定稳定顺序；
4. 同一画作在任何设备、任何重进情况下顺序一致。

禁止使用每次进入都变化的 `Math.random()`，否则只保存 `filledCells` 无法恢复相同画面。

第一版不实现让玩家自由选择任意区域；等核心闭环验证后，可以增加“主体/背景/细节”区域选择，但那会要求保存分区进度。

### 8.4 画面层级

单幅画作建议使用以下层：

```text
主题画框
  ├─ 底板/卡纸
  ├─ 未完成豆位底色
  ├─ 已填充的像素拼豆层
  ├─ 统一格线层
  ├─ 高清原画层（完成前隐藏）
  └─ 标题铭牌与进度
```

单个逻辑豆位固定占 5×5 设计像素，其中 1 像素表现格线或豆间间隙，4×4 表现有效色块：

- 未填豆位使用相册主题的低饱和不透明底色和轻微孔位/凹槽，形成覆盖画作的巨大色块棋盘；
- 已填豆位切换为像素预览中的正确颜色，并增加轻微高光，使它明确像一颗已经放入的拼豆；
- 未填与已填不能只靠极小明度差区分；
- 画作未完成时不直接显示高清原画；
- 完成后格线和拼豆层一起融合，才显示 650×780 高清图；
- 像素预览放大时使用邻近采样，禁止双线性模糊。

性能硬约束：

- 禁止创建 20,280 个 Cocos 节点、Sprite 或 Label。
- 拼豆状态必须由低分辨率遮罩纹理、批量绘制、RenderTexture 或等价单批方案表示。
- 格线使用单张纹理或一次绘制，不创建单格边框节点。
- 单次填入 500 颗时允许分批动画，但可见动画对象建议不超过 40 个。
- 继续只保留当前画作和左右邻居的大图加载策略。

### 8.5 资源组成

每幅画至少包含：

- `pic_N.jpg`：650×780 高清完成图；
- `preview_N.png` 或等价低清像素预览：130×156，必须使用邻近采样显示；
- 画作元数据：标题、焦点、稳定种子。

每册画作共享：

- 一套外框纹理；
- 一套内衬/卡纸颜色；
- 一套角花或装饰；
- 一套标题铭牌风格。

画框不得烘焙进每张 JPG。

### 8.6 拼画交互

未完成画作显示：

- `已完成 7,500 / 20,280`；
- 百分比进度；
- 当前心情豆余额；
- 主按钮“投入 500 颗心情豆”；
- 余额不足 500 时按钮自动改为实际可投入数量；
- 余额为 0 时显示“去整理心情，收集心情豆”。

为处理积攒大量余额的玩家，可增加次按钮“全部投入”。服务端仍需限制单次请求并安全裁剪，客户端表现可以把大额投入拆成每批 500 的连续动画。

### 8.7 完成演出

当 `filledCells` 达到 20,280：

1. 停止输入，避免重复提交；
2. 完成最后一批拼豆动画；
3. 画板轻微压合，播放热气/柔光；
4. 格线和像素拼豆层由中心向外融合；
5. 高清原画淡入；
6. 显示“画作已定型”；
7. 解锁下一幅画；
8. 写入服务端完成时间；
9. 重进后直接显示高清原画，不重复收费。

完成演出只播放一次；异常退出后以服务端 `completedAt` 为准，可补播简化完成反馈但不得再次扣豆。

## 9. 画作与画框素材标准

### 9.1 原画转换

现有 750×1000 母版转换为 650×780 时禁止直接拉伸。

默认批处理：

```text
750×1000
→ 居中裁切为 750×900
→ 等比缩放为 650×780
```

每幅图必须人工检查：

- 人物头顶、脚部和手持物未被裁断；
- 建筑屋顶、塔尖、树冠等主体未被裁断；
- 原有签名、水印或关键角落信息未被裁掉；
- 主体在更宽比例中仍然平衡；
- 不出现非等比变形；
- JPEG 压缩没有明显色带和噪点。

保留 750×1000 母版到非运行归档目录；运行路径继续使用原有文件名和 `.meta`，尽量保留 UUID，避免 60 幅画引用整体失效。

### 9.2 画框尺寸

- 原画内容区：650×780。
- 推荐外框：约 700×830，最终不得超过 700×850。
- 750 宽设计画布下，外框左右至少保留 25 像素。
- 翻页箭头不再与画框左右并排挤压，可放在画框下方或嵌入下角。
- 外框不得遮盖原画关键内容；内压边建议 8～16 像素。

### 9.3 首批画框方向

`四季物语`：

- 浅木色或奶油木色；
- 低饱和植物角花；
- 内衬可随春夏秋冬轻微换色，但结构一致。

`京城掠影`：

- 深胡桃木或灰蓝木质；
- 低亮度铜色包角；
- 铭牌可使用印章或旧城牌匾语言，但不要过度古董化。

### 9.4 资源校验

`scripts/validate-assets.js` 必须新增：

- 所有 `pic_N.jpg` 精确为 650×780；
- 所有像素预览精确为 130×156；
- 画作大图与预览禁止进入动态 atlas；
- 每个画册定义必须有对应画框资源；
- 主题数量、文件连续编号和 Bundle 路由保持一致；
- 不允许把 750×1000 运行图混入新包。

## 11. 阶段 B：心情画板与 DIY 作品

> 本章属于阶段 B。必须等阶段 A 验收完成并收到用户的新开发指令后实施。

### 11.1 画板尺寸

第一版提供：

- 8×8：新手、图标和表情；
- 16×16：默认尺寸；
- 32×32：进阶作品。

禁止第一版支持任意宽高，避免作品校验、交互和展示比例失控。

### 11.2 编辑工具

第一版最低工具集：

- 单点画笔；
- 按住拖动画笔；
- 橡皮；
- 撤销；
- 重做；
- 油漆桶填充；
- 取色；
- 缩放和移动画布；
- 网格开关；
- 成品预览。

镜像、复制区域、旋转、图层等工具不在第一版范围。

### 11.3 免费草稿原则

- 草稿编辑不立即扣除彩豆。
- 玩家可以使用已解锁的 12 种基础色自由尝试。
- 界面实时统计作品需要的每种彩豆数量，并与库存比较。
- 撤销、擦除和改色只改变需求统计，不产生退款事务。
- 草稿保存在本地，第一版允许最多 20 份；超出时要求玩家自行删除或覆盖。

### 11.4 定型规则

玩家点击“熨烫定型”后：

1. 客户端重新统计所有非空像素；
2. 展示材料清单和缺口；
3. 材料不足时引导去心情调色铺，不提交定型；
4. 材料足够时提交完整像素数据和唯一 `actionId`；
5. 服务端重新校验尺寸、颜色 ID 和每色数量；
6. 服务端事务扣除彩豆并保存作品；
7. 返回成功后播放定型演出；
8. 原草稿标记为已完成或删除；
9. 已定型作品第一版不可直接编辑，可“复制为新草稿”。

### 11.5 空像素与材料

- 空像素使用专用值，例如 `null` 或 `0`，不消耗彩豆。
- 每个非空像素消耗 1 颗对应颜色彩豆。
- 8×8 最大消耗 64 颗彩豆。
- 16×16 最大消耗 256 颗彩豆。
- 32×32 最大消耗 1,024 颗彩豆。

按 10:1 兑换、每局约 500 心情豆估算，满铺作品约需要：

| 尺寸 | 满铺彩豆 | 等价心情豆 | 约等于 500 豆/局时 |
|---|---:|---:|---:|
| 8×8 | 64 | 640 | 1.28 局 |
| 16×16 | 256 | 2,560 | 5.12 局 |
| 32×32 | 1,024 | 10,240 | 20.48 局 |

### 11.6 作品存储

作品保存网格数据，不保存一张永久 PNG：

```text
workId
playerId
name
width
height
pixelData
createdAt
```

`pixelData` 可以使用紧凑数组或字符串编码，但第一版不得为了几十 KB 数据引入复杂二进制协议。32×32 只有 1,024 个像素，优先选择易测试、易演进的格式。

展示和分享时由客户端本地渲染成纹理或临时图片。服务端不提供公共作品 CDN。

### 11.7 UGC 安全边界

- 第一版作品默认私有，仅本人可见。
- 可以生成本地分享图，但不提供游戏内公共浏览入口。
- 不允许导入外部图片。
- 不允许作品名超过 20 个字符；保存前过滤控制字符。
- 将来开放公共广场前必须另行设计内容审核、举报、版权和未成年人保护流程。

### 13.6 官方拼画接口

```text

POST /realm/arts/contribute
```

`GET /realm/state` 返回：

- 玩家心情豆余额；
- 已开放画册；
- 各画作 `filledCells` 和 `completedAt`；
- 当前配置版本。

`POST /realm/arts/contribute` 请求：

```text
actionId
artId
requestedBeans
```

服务端处理：

1. 验证 `actionId`；
2. 验证 `artId` 在服务端白名单；
3. 验证所属画册已开放；
4. 验证前一幅画已完成；
5. 读取当前进度和余额；
6. 计算 `actualSpend = min(requestedBeans, balance, remainingCells, maxPerAction)`；
7. 同一事务扣心情豆并增加 `filledCells`；
8. 达到 20,280 时写入 `completedAt`；
9. 写入 `official_art_actions`；
10. 返回余额、实际投入、最新进度和完成状态。

余额不足时不得部分修改后再报错。允许服务端安全裁剪为较小投入，但返回值必须明确 `actualSpend`。

- 重新统计每色需求；
- 验证库存；
- 在同一事务扣彩豆、保存作品和幂等结果；
- 同一 `workId` 和 `actionId` 不得重复定型收费。

## 14. 离线、弱网与幂等策略

### 14.1 对局结算

现有项目已经存在“本地先结算、云端稍后提交”的行为，但没有完整离线补传。心情豆成为消费余额后，必须增加本地待提交队列：

```text
zyx_pending_round_settlements
```

每条包含：

```text
roundId
startedAt
endedAt
score
collectedMoodBeanCount
```

规则：

- 本地结算后立即入队；
- 云端成功后删除；
- 启动、回首页和网络恢复时重试；
- 依靠 `roundId` 保证服务端幂等；
- 队列设置合理上限并记录异常，但不得静默覆盖未提交记录。

### 14.2 消费类操作

官方拼画、调色和 DIY 定型第一版要求在线：

- 离线时可以浏览缓存和编辑本地草稿；
- 不允许离线扣心情豆或彩豆；
- 不创建复杂的离线消费队列；
- 弱网请求中按钮进入 loading，防止重复点击；
- 请求超时后允许用同一 `actionId` 重试；
- 服务端返回保存过的幂等结果。

这是第一版控制双权威风险的必要边界。

- 像素预览体积应显著小于高清图。
- 未完成画作优先加载预览；高清图可以在接近完成或打开已完成作品时加载。
- 画框按册复用，不随 60 幅画重复打包。
- 记录每个 Bundle 改造前后大小。
- 保持主包、首页、秘境核心和各册画作分包边界。

## 20. 埋点与数值调优

第一版框架完成后，至少记录：

### 消除

- 每局收集表情数；
- 每局基础心情豆；
- 广告加成心情豆；
- 每局时长；

### 官方拼画

- 进入秘境比例；
- 有余额但未投入比例；
- 每次投入数量；
- 单幅完成所需天数和局数；
- 25%、50%、75%、100% 到达率；

### 阶段 B：调色与 DIY

- 调色铺进入率；
- 各颜色兑换量；
- 草稿创建率；
- 草稿定型率；
- 各尺寸使用率；
- 因材料不足放弃定型比例；
- 平均每件作品消耗彩豆。

### 调参顺序

1. 先测普通用户每局实际收集的带表情心情块数量；
2. 再调心情块出现率、单局长度或官方画作豆位数，让完成局数接近目标；
3. 阶段 B 启动后再观察 10:1 是否抑制 DIY 定型；
4. 最后才考虑广告加成、特殊彩豆和画框收费。

不要仅根据理论广告收入把画作时长拉到 60 局。应同时观察完成率、次日留存和平均广告观看数。

## 22. 最终完成定义

### 22.1 阶段 A 完成定义

- 玩家可见流程中没有开心瓶和毛玻璃解锁语义；
- 消除、经验和心情豆数值彼此独立且一致；
- 客户端和服务端旧用户数据已完整清空，新档不会再次被启动逻辑误删；
- 60 幅画作完成 650×780 转换并通过人工构图检查；
- 两册画作拥有独立复用画框；
- 官方画作可用心情豆从 0 拼到 20,280 并可靠恢复；
- 所有扣豆操作由服务端事务处理并支持幂等重试；
- 调色铺、彩豆和 DIY 没有被提前实现，也没有不可用占位入口；
- `npm test`、`npm run validate:assets`、Web 构建和微信构建通过；
- 标准屏、短屏、长屏和真机主要路径验收通过；
- README、交接文档、GM 工具和玩家文案与新术语一致。

满足以上条件后，阶段 A 即为完整可交付成果。此时必须停止开发并等待用户布置阶段 B。

### 22.2 阶段 B 完成定义

在阶段 A 仍全部通过的基础上：

- 10:1 调色完整可用；
- DIY 草稿免费、定型准确扣彩豆；
- 作品使用网格数据保存，不依赖永久 PNG CDN；
- 阶段 A 已产生的心情豆和官方画作数据没有被清空、折算或破坏；
- 公共 UGC、图片导入和复杂特殊豆没有被提前实现；
- 阶段 A 全量回归与阶段 B 新增测试均通过。

## 23. 实施时的最终约束

低成本模型必须遵守：

1. 一次只做一个阶段中的一个明确任务。
2. 先写或更新测试，再改变核心余额逻辑。
3. 不修改任务范围之外的文件和格式。
4. 不引入新的 UI 框架、状态框架、数据库 ORM 或构建系统。
5. 不创建每豆一个节点的官方画板。
6. 不允许客户端单方面决定最终余额。
7. 不允许扣豆接口缺少幂等操作 ID。
8. 不编写任何旧存档、旧数据库或旧客户端兼容逻辑。
9. 不把画框烘焙进每幅原画。
10. 不在第一版扩展公共 UGC、图片导入、特殊豆和作品交易。

任何无法确定的产品选择必须停在配置或文档层提出，不得由模型自行扩大范围。
