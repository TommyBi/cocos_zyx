# 阶段 A 代码审查整改基线

> 状态：必须实施的上线前整改方案（2026-08-21）  
> 适用项目：《烦恼排排消》Cocos Creator 2.4.13 微信小游戏  
> 目标读者：负责落实整改的普通模型、负责最终复审的高能力模型  
> 范围：只修复阶段 A 的安全、数据一致性、幂等、离线补传、拼画恢复和性能问题；不得开始彩豆、调色铺或 DIY 画板。

本文是 2026-08-21 代码审查后的增量整改基线。与旧实施方案冲突时，本文关于安全、重开、云同步和事务的规定优先。

---

## 1. 已确认的产品与工程决定

以下决定不再留给执行模型自行选择。

### 1.1 GM 只允许出现在 Web 调试环境

- Cocos Creator Web 调试构建可以显示 GM 悬浮入口；
- 微信小游戏端无论开发版、体验版还是正式版，均不得显示 GM 入口；
- Web 正式构建也不得显示 GM，必须同时满足“Web 平台 + Debug 构建”；
- 生产服务端不得注册任何普通玩家可访问的 `/debug/*` 路由；
- 隐藏按钮不属于安全措施，服务端路由隔离才是最终安全边界。

推荐客户端条件：

```text
CC_DEBUG === true && cc.sys.isBrowser === true
```

允许使用项目中等价的显式构建标记，但禁止只判断 `cc.sys.isBrowser`，也禁止只把按钮透明度设为 0。

### 1.2 新经济没有任何历史包袱

- 不接收、不迁移、不折算旧开心瓶、旧画册、旧等级、旧余额或旧拼图数据；
- 新服务端账号固定从 Lv.1、经验 0、豆余额 0、累计豆 0、最高分 0 开始；
- `bootstrap` 不得接收客户端资产、等级、经验和最高分作为建档基线；
- 可以直接删除旧数据库并按新 schema 重建；
- 不保留双版本字段、旧接口回退或“以后可能迁移”的兼容分支。

### 1.3 暂停菜单“重新开始”直接放弃本局

玩家在暂停菜单选择“重新开始”时：

- 不调用 `finishRound()`；
- 不获得豆子；
- 不获得经验；
- 不更新最高分；
- 不增加服务端对局数或周榜；
- 不生成 `roundId`；
- 不进入待提交结算队列；
- 只清空当前棋盘并开始一局全新的挑战。

“结束本局”和正常失败仍走完整结算；“重新开始”不是一种结算方式。

### 1.4 阶段 B 继续冻结

本轮整改禁止增加：

- 彩豆；
- 10:1 调色；
- DIY 画板、草稿和作品表；
- DIY 入口或占位按钮；
- 公共作品广场。

## 2. 整改问题总表

| 编号 | 优先级 | 问题 | 完成标准 |
|---|---|---|---|
| R0 | P0 | 正式包暴露 GM，生产接口允许普通玩家改资产 | 小游戏包无 GM；生产 `/debug/*` 返回 404；本地 Web Debug 可用 |
| R1 | P1 | `bootstrap` 信任客户端本地资产，可任意铸币并导致首次离线双算 | 新账号永远零资产；本地档案字段被删除或忽略 |
| R2 | P1 | 离线结算只在首次 bootstrap 后补传，坏记录会堵住整队列 | 单一队列工作器可在启动、回首页、恢复网络时持续补传 |
| R3 | P1 | 暂停重开本地入账但不提交云端 | 重开完全不结算、不发奖、不入队 |
| R4 | P1 | 拼画超时后新建 `actionId`，可能发生第二次真实扣豆 | 模糊失败始终重用同一持久化 `actionId` |
| R5 | P2 | 服务端先响应成功，数据库最多 500ms 后才真正落盘 | 关键经济事务落盘成功后才能返回 2xx |
| R6 | P2 | 幂等 ID 是全局主键，没有绑定玩家和原请求载荷 | 结算和拼画均按玩家作用域幂等，并校验重复请求载荷一致 |
| R7 | P2 | 填充顺序退化为所有画作统一逐行擦除 | 按正式方案补焦点/稳定种子，或经产品确认后统一修改规范 |
| R8 | P2 | 单次最多 800 个 Graphics 飞行节点，遮罩反复全量扫描 | 限制视觉节点并优化分块循环，通过微信真机性能验收 |

R0～R6 是上线阻断项。R7～R8 不得与安全事务混在同一个大改动中，应在前述问题稳定后单独实施和验证。

## 3. R0：彻底隔离 GM 与调试接口

### 3.1 客户端

修改 `GameMainScene.ts`：

- `onLoad()` 不再无条件调用 `createGmBubble()`；
- 只有 Web Debug 条件成立时才创建；
- 微信小游戏构建中不能创建节点、事件监听和 GM 弹窗；
- 普通设置面板不得包含任何 GM 入口；
- 不允许使用连续点击、长按、透明按钮等“隐藏入口”绕过要求。

Web Debug 的 GM 行为分为两种：

1. 没有配置本地 API 覆盖地址时，只修改本地调试数据，不向生产服务器同步；
2. 指向本地开发服务时，可以调用仅本地启用的调试路由。

客户端检测到 API 地址仍是生产地址时，GM 必须显示“仅本地调试，未同步云端”，禁止调用生产 `/debug/*`。

### 3.2 服务端

生产环境必须完全不注册：

```text
POST /v1/cocos-zyx/debug/profile
POST /v1/cocos-zyx/debug/reset
```

如需保留本地联调，必须同时满足：

```text
NODE_ENV !== production
ENABLE_GM_ROUTES === 1
```

任一条件不满足时路由不存在并返回 404，而不是返回 401/403 暗示接口仍存在。

不得把普通玩家 Bearer Token 当成管理员权限。未来如需线上 GM，必须另立管理员身份、审计日志和允许操作范围，不在本轮实现。

### 3.3 测试

- 微信构建产物中不存在 `gmFloatingBubble`、`GM 补给` 和调试按钮文案；
- `NODE_ENV=production` 时两个调试路由均为 404；
- 非生产但未设置 `ENABLE_GM_ROUTES=1` 时仍为 404；
- 本地开发且显式启用时，Web Debug GM 可以工作；
- 普通玩家 API 无法改变余额、等级、经验或最高分的绝对值。

## 4. R1：bootstrap 只负责身份建档

### 4.1 客户端请求

`CloudService.bootstrap()` 只提交：

```text
deviceId
nickname
avatarUrl
```

删除 `localProfile` 参数及所有调用方传入的：

```text
level
experience
moodBeanBalance
totalMoodBeans
highestSingleGameScore
```

头像昵称不属于经济数据，可以更新；其余进度只来自服务端结算和事务接口。

### 4.2 服务端建档

不存在该 `deviceId` 时固定创建：

```text
level = 1
experience = 0
mood_bean_balance = 0
total_mood_beans = 0
highest_single_game_score = 0
```

存在账号时只更新允许变化的昵称和头像，返回服务端权威档案，不合并客户端数值。

如果客户端仍提交 `localProfile`，第一版可以直接忽略；完成客户端升级后应从接口结构中彻底删除，避免未来误用。

### 4.3 数据重建

- 仓库内本地开发数据库和测试数据库允许直接删除重建；
- 生产 Docker 数据卷只能在明确的正式维护窗口人工确认后删除；
- 执行模型不得自行连接、删除或部署线上数据；
- 新 schema 不创建任何 `happy_bottle_*`、旧拼图或迁移字段。

### 4.4 测试

- 新设备伪造一亿余额建档后，服务端仍返回 0；
- 新设备伪造 1000 级和一亿最高分后，仍返回 Lv.1 和 0；
- 已有账号再次 bootstrap 不被客户端零值或大值覆盖；
- 首次离线完成一局、随后联网建档并补传，只奖励一次豆子和一次经验。

## 5. R2：建立真正可恢复的离线结算队列

### 5.1 单一队列原则

所有对局结算都必须走同一条路径：

```text
生成结算记录
→ 先可靠写入 pending 队列
→ 再尝试提交
→ 服务端确定成功后删除对应记录
```

禁止同时存在“当前局直接提交”和“后台队列另行提交”两套并发路径。队列工作器必须是 single-flight：同一时刻最多有一个 flush 过程。

### 5.2 触发时机

以下时机都要调用同一个 `flushPendingRoundSettlements()`：

- 云档案 bootstrap 成功后；
- 每次进入首页时，即使 `cloudProfileReady` 已经为 true；
- 微信 `onShow`；
- 微信网络状态从离线变为在线；
- 新结算入队后；
- 进入时空秘境准备消费豆子之前。

`cloudProfileReady` 只能跳过重复建档，不能跳过队列补传。

### 5.3 队列容量

- 队列建议上限 100 条；
- 开始新一局前检查是否仍有至少一个空位；
- 已达上限且无法同步时，提示“需要联网同步进度后继续”，不允许开始新局；
- 不得在玩家完成一局并本地入账后才发现队列满；
- 不得静默丢弃最旧或最新记录。

### 5.4 错误分类

临时错误：

- 网络不可用；
- 超时；
- 5xx；
- 服务暂不可达。

处理：保留当前记录并停止本次 flush，等待下次触发。

永久错误：

- 记录字段损坏；
- 服务端明确返回不可重试的 4xx；
- 超过服务端允许的最大离线保留期。

处理：

1. 从活动队列移入本地 dead-letter 记录；
2. 记录错误原因与时间；
3. 继续处理后续记录，禁止堵塞整队列；
4. 重新拉取服务端档案校正本地展示；
5. 给玩家可理解的“有一局记录未能同步”提示，不伪装成功。

### 5.5 时间校验

删除当前“开始时间早于现在 6 小时就永久拒绝”的规则。它不是有效的反作弊手段，只会破坏真实离线补传。

建议集中配置：

```text
MIN_ROUND_DURATION_MS = 5 秒
MAX_ROUND_DURATION_MS = 4 小时
MAX_FUTURE_SKEW_MS = 2 分钟
MAX_OFFLINE_SETTLEMENT_AGE_MS = 7 天
```

服务端可以拒绝超过 7 天的异常积压，但客户端必须按永久错误隔离，不得阻塞后续记录。时间范围、单局收集上限和请求频率共同作为基础风控；不要把客户端时间戳当成不可伪造凭据。

### 5.6 本地展示与消费

- 本地可以立即展示本局获得的豆子和经验；
- 未同步奖励必须可以从 pending 队列重新计算，不能只存在于一个无法追溯的余额数字中；
- 时空秘境消费前先完成队列补传并拉取 `/realm/state`；
- 未确认奖励不能离线消费；
- 云端回执覆盖本地档案后，最终展示必须等于服务端余额加仍未确认的 pending 预览值，不能瞬间重复或永久丢失。

### 5.7 测试

- 云档案已 Ready 后断网结算，回首页并恢复网络能够自动补传；
- 第一条为永久坏记录时，第二、第三条仍能成功提交；
- 服务器 500 后记录保留，稍后成功且只奖励一次；
- 7 天内离线记录可补传；
- 超期记录进入 dead-letter，不堵塞后续队列；
- 队列满时无法开始新局，不发生“本地加了奖励但没有记录”；
- 两次并发触发 flush 不会发送两套并行队列工作器。

## 6. R3：暂停重开不结算

修改 `ZyxGame.restartFromPause()` 或等价入口：

```text
关闭暂停弹窗
→ 丢弃当前棋盘和本局临时统计
→ resetRound()
→ 重建玩法 UI
```

禁止调用：

```text
finishRound()
onSettlementExit()
submitSettlementToCloud()
enqueuePendingRoundSettlement()
```

如果需要二次确认，可显示“重新开始后，本局进度不会保存”，但第一版不要求新增弹窗。

回归测试：

- 本局收集 10 豆后暂停重开，余额、经验、最高分和 pending 队列均不变；
- 重开后新一局统计从 0 开始；
- “结束本局”仍正常获得奖励并提交云端；
- 正常失败和结算面板“再来一次”仍先结算上一局，再开启下一局。

## 7. R4：拼画模糊失败必须重用 actionId

### 7.1 客户端持久化

新增阶段 A 本地键：

```text
zyx_pending_realm_action
```

第一版同一玩家最多存在一条未确认拼画操作：

```text
actionId
artId
requestedBeans
createdAt
```

操作顺序：

```text
生成 actionId
→ 先写入 zyx_pending_realm_action
→ 禁用投入按钮
→ 提交服务端
→ 收到确定成功结果后更新余额/进度并清除 pending action
```

网络超时或响应丢失时：

- 保留原 `actionId`；
- 按钮显示“重试放置”或进入自动重试；
- 重试必须提交完全相同的 `actionId + artId + requestedBeans`；
- 禁止生成第二个 actionId；
- 重新进入秘境时先处理 pending action，再允许发起新投入。

### 7.2 与服务端幂等配合

幂等键必须绑定玩家：

```text
PRIMARY KEY (player_id, action_id)
```

重复操作时：

- 同一玩家、同一 actionId、相同 `artId/requestedBeans`：返回第一次保存的结果；
- 同一玩家、同一 actionId、载荷不同：返回 409，不执行任何扣减；
- 不同玩家可以使用相同 actionId，互不影响。

`round_settlements` 同样改为玩家作用域幂等：

```text
PRIMARY KEY (player_id, round_id)
```

服务端的完整字段校验、结果快照和事务顺序按 R6 实施；R4 的重点是客户端遇到模糊失败时绝不更换操作身份。

### 7.3 测试

- 服务端已提交但客户端模拟丢失响应，再次发送同一 actionId 不重复扣豆；
- 客户端重启后能恢复 pending action 并完成同一笔请求；
- 同 actionId 改变 artId 或 requestedBeans 返回 409；
- 两名玩家使用相同 actionId 不互相读取结果；
- 两名玩家使用相同 roundId 不会导致其中一人丢失结算。

## 8. R5：关键事务成功后立即可靠落盘

当前 sql.js 的 500ms 防抖只适合非关键展示数据，不适合豆子和画作事务。

最低改造方案：

- `withTransaction()` 完成 `COMMIT` 后，为关键接口调用同步 `persistNow()`；
- `persistNow()` 成功后才返回 2xx；
- 写文件失败时接口返回 5xx，客户端保留相同 roundId/actionId 重试；
- 防抖持久化可以继续用于昵称、头像等非经济写入；
- 不允许仅依靠 `SIGTERM` 退出钩子保证数据安全，OOM/SIGKILL 不会执行该钩子。

关键接口至少包括：

```text
新玩家建档
对局结算
官方拼画投入
账号重置（仅本地调试环境）
周榜奖励写入
```

如果普通模型选择替换为原生 SQLite/WAL，必须先单独说明依赖、Docker 镜像、事务和备份影响；不得在同一次小修中擅自更换数据库技术栈。第一版优先采用“关键事务立即导出”的最小修复。

测试：请求返回成功后，不调用优雅退出钩子，立即用新数据库实例读取同一文件，仍能看到刚才的结算或扣豆结果。

## 9. R6：把幂等约束绑定到玩家和原始请求

R4 解决“客户端是否重用同一个操作身份”，R6 解决“服务端如何证明重复请求确实是同一笔操作”。两者缺一不可。

### 9.1 数据库约束

对局结算和拼画投入都不得继续使用全局唯一的业务 ID。可以采用复合主键，也可以保留内部自增主键并增加复合唯一索引，但最终数据库必须强制保证：

```text
UNIQUE (player_id, round_id)
UNIQUE (player_id, action_id)
```

这样两个玩家偶然生成相同 ID 时不会互相命中记录，也不会读取对方的结算结果。

每条幂等记录至少保存：

- 玩家 ID 和业务 ID；
- 会影响经济结果的规范化请求字段；
- 第一次事务完成后的权威结果快照；
- 创建时间。

不得只保存“这个 ID 用过了”而不保存原始载荷和结果。

### 9.2 重复请求处理顺序

每次请求都在同一数据库事务中按以下顺序处理：

```text
按 playerId + roundId/actionId 查询历史记录
→ 已存在且经济载荷完全一致：直接返回第一次保存的结果快照
→ 已存在但经济载荷不同：返回 409，不改变任何数据
→ 不存在：执行权威计算和资产变更
→ 保存请求载荷与结果快照
→ 提交事务并按 R5 可靠落盘
→ 返回 2xx
```

对局结算至少比较开始/结束时间、基础收集统计、分数以及所有参与服务端奖励计算的字段；拼画投入至少比较 `artId` 和 `requestedBeans`。先把字段规范化为稳定结构再比较，禁止依赖 JSON 属性顺序。

客户端提交的最终奖励额不属于可信载荷，服务端仍须根据规则自行计算；保存它不能使它变成权威数据。

### 9.3 测试

- 同一玩家用相同 roundId 和相同载荷重试，只结算一次并返回相同结果；
- 同一玩家用相同 roundId 修改收集数或其他经济字段，返回 409；
- 同一玩家用相同 actionId 修改画作或投入量，返回 409；
- 两名玩家使用相同 roundId 时，各自都能正常结算；
- 两名玩家使用相同 actionId 时，各自都能正常投入；
- 409、事务失败和落盘失败均不得留下部分扣款、部分进度或伪成功记录。

## 10. R7：填充顺序与正式方案重新对齐

此项在 R0～R6 全部通过后单独实施。

每幅画作配置：

```text
focusX: 0..1
focusY: 0..1
revealSeed: 稳定整数
```

排序规则：

1. 计算每个豆位中心到焦点的归一化距离；
2. 使用 `revealSeed + cellIndex` 生成跨设备一致的微小稳定扰动；
3. 按“距离 + 扰动”升序；
4. 相同值最后按 `cellIndex` 排序，确保完全确定；
5. 返回 0..20,279 的完整无重复排列。

禁止使用 `Math.random()` 生成填充顺序，也禁止只在内存保存排序结果。

如果产品最终决定保留当前从上到下逐排揭开，必须先由用户明确确认，然后同时修改总体方案、README、测试名称和实现注释。执行模型不得自行用“已经能运行”为理由修改规范。

测试：

- 每幅画的排序都是完整排列；
- 同一 artId 多次计算完全一致；
- 不同 seed 的顺序存在显著差异；
- 首批豆位明显集中在焦点附近；
- 重启和 Web/微信两端恢复出的已填区域一致。

## 11. R8：拼画性能收口

此项不得改变服务端进度结果，只优化视觉抽样与遮罩绘制。

### 11.1 飞行豆

- `MAX_VISUAL_BEANS` 从 800 降到不高于 120；
- 优先使用节点池，避免每次批量创建和销毁；
- 优先复用 SpriteFrame 或批量渲染，不为每颗豆新建复杂 `cc.Graphics`；
- 未显示的逻辑豆位仍按进度前沿揭开，服务端实际投入数不能减少；
- 动画结束必须以服务端 `filledCells` 强制校正。

### 11.2 遮罩分块

`drawCoverChunk()` 只遍历当前分块的行列：

```text
rowStart..rowEnd
0..ART_GRID_COLS
```

禁止每个分块都从 `filledCells` 扫描到 20,280 后再过滤行号。增量更新只重绘受影响分块。

### 11.3 生命周期

- 放置动画期间返回画册、切换画作或销毁页面时，所有定时器和 Tween 必须取消；
- 旧页面回调不得在数秒后重新打开已经离开的画册；
- 页面销毁后仍以本地缓存和服务端状态为准，不依赖动画完成回调保存进度。

### 11.4 验收

- 单次投入 5,000 豆时，在屏飞行节点不超过 120；
- 动画结束进度与服务端一致；
- 连续快速翻 20 页，内存不会持续线性增长；
- 动画中返回首页，数秒后不会自动跳回秘境；
- 至少在一台性能较低的微信真机上验证，无明显长时间冻结或触摸失效。

## 13. 普通模型实施顺序

必须按以下顺序拆分提交和验收，不允许一次性重写所有模块。

### A-Review-0：先补失败测试

- 生产调试接口可访问；
- bootstrap 可以伪造资产；
- 已 Ready 后的离线队列不补传；
- 坏记录堵住后续记录；
- 暂停重开发奖；
- 拼画响应丢失后第二次扣豆；
- 请求成功但数据库文件尚未更新；
- 跨玩家 roundId/actionId 冲突。

### A-Review-1：GM 隔离

只修改 GM 显示条件、调试路由注册和相关测试。完成后先提交复审，不与队列重构混合。

### A-Review-2：清洁 bootstrap 与新 schema

删除 `localProfile` 经济建档；为对局结算和拼画操作建立玩家作用域唯一约束、规范化请求字段和结果快照字段；重建测试数据库。不得编写迁移。

### A-Review-3：结算队列

实现 single-flight、完整触发点、错误分类、dead-letter 和容量前置检查。

### A-Review-4：重开语义

删除暂停重开中的 `finishRound()`，补四条入口差异测试。

### A-Review-5：拼画 pending action

实现持久化 actionId、同 ID 重试和重启恢复；完成 R6 对 `roundId/actionId` 的同载荷重放、异载荷 409、跨玩家同 ID 测试。

### A-Review-6：可靠落盘

关键事务返回前持久化，并补进程重载测试。

### A-Review-7：填充顺序

在安全与数据链路全部稳定后，单独实现焦点/seed 方案；如等待产品确认则明确停止，不得私自改变规范。

### A-Review-8：性能与生命周期

降低飞行节点、优化分块循环、取消销毁页面的异步回调，完成真机验收。
