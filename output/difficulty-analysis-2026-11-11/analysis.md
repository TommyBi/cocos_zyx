# 局内难度、新手连消与权益安全分析

日期：2026-11-11。依据当前工作区，包含尚未提交的修改；没有核验线上部署版本。此次只新增分析产物，未修改游戏或服务端业务代码，未请求线上接口。

## 结论

当前生成器保障的是下一排的横移空间，没有保障移动后能消除，也没有保障下一次操作仍能消除。前三步教学与后续随机局面的机会密度差异很大。应把新手体验从“少出块”改成“连续提供容易识别的可消除局面”，让难度由一步解的数量、移动距离、规划深度和棋盘压力共同决定。

权益安全需先修结算与道具授权缺口。提高换豆门槛、限制体力和确定性重放都不能单独阻止当前绕过，也不能阻止符合规则的自动求解脚本。体验可以持续友好，权益必须有独立的服务端预算。

当前占格概率：P5=clamp((turn−4)/8)，P6=clamp((turn−13)/10)，先抽六格再抽五格。turn 0–4 固定四格，turn 8 四/五格各半，turn 12–13 固定五格，turn 18 五/六格各半，turn 23 以后固定六格。这里 turn 是自动补排数，不是玩家操作数。

因此，出块分布确实已有后期封顶；但堆高、空洞、解的数量仍继续变化，不能据此认定玩家感受到的后期难度已经恒定。密度也不等于难度：有些稀疏局面很难凑满行，有些密集局面轻移即可清掉。

颜色池会在累计消除 3/7/12 行时趋向较平静的颜色，颜色不影响满行规则，仅对魔法棒的作用范围有间接影响。当前 UI 没有与上述难度坡度绑定的清晰阶段提示；成功清掉更多排还可能因自动补排而更快推进坡度。

## 本地样本

教学、普通开局各运行 1,000 组种子。种子为 `(样本序号 × 0x9e3779b1) mod 2^32`，避免直接使用连续小整数造成首个随机值偏窄。使用当前客户端模块，教学过渡按实际 UI 顺序执行。

每个局面枚举所有合法横移及位移，模拟重力后检测满行；“一格解”指横移一格就直接消除。后续策略优先用现有提示找到的直接消除，否则用独立确定性随机源选择合法移动；不使用付费/广告道具，不主动点炸弹，执行正式补排及至少保留两排规则。因此这些是指定策略的本地样本，不是线上用户成功率，也不是最优策略结论。

| 指标 | 教学局 | 普通开局 |
| --- | --- | --- |
| 教学后第一自由操作 / 普通第一操作存在直接消除解 | 22.0% | 100% |
| 同局面存在一格直消解 | 16.0% | 100% |
| 普通第二操作存在直接消除解 | — | 8.4% |
| 普通第二操作存在一格直消解 | — | 5.1% |

一步直接消除不包括自动补排后的偶然消除；样本不是对全部策略的穷举。最强证据是教学过渡后，78% 的棋盘根本没有一步直消解，提示也无法制造机会。

复现：在仓库根目录运行 `node output/difficulty-analysis-2026-11-11/simulate.cjs`。编译依照现有测试方式，允许缺少 Cocos 全局类型但有 JS 产物；这不代表完整 TypeScript 类型检查通过。原始结果见 `simulation-results.json`。

## 优先修复的安全与一致性问题

1. **新局可由客户端选择 legacy。** `/games/start` 接收 legacy 且缺省就是 legacy；旧协议无重放时允许直接提交收集数，按原始数发整豆。本地临时数据库、NODE_ENV=production、关闭 GM，模拟服务端经过六秒后，空操作提交获得 5,000 豆并记入 1,000,000 分。应由服务端根据受信版本/已有开局记录决定协议，新创建对局禁止自行降级；历史兼容需限已有凭证并设退役边界。
2. **progress_v1 的零收集可跳过重放写榜。** 相同隔离环境中，零收集、空操作、提交 1,000,000 分也被接受。所有分数、经验、资产和榜单变化都必须由服务端重放或权威计算产生；空操作只能返回权威初始结果。
3. **重放未验证道具和救场的授权。** gameEngine 的 hammer、purify、revive、clear 没有服务端库存、可用次数或领取凭证；append 也没有强制遵守 UI 的操作后补排顺序。需要将操作序列视为状态机，校验合法阶段、道具库存、救场触发条件及次数。广告/分享触发的权益需服务端可验证的领取记录；无法验证的行为只能进入有限免费额度。
4. **生产模式仍接受纯 deviceId 访客建档。** 本地生产模式复现包含此路径。实物权益账户需受信微信身份；访客体验资产不进入可兑现余额，不能靠更换 deviceId 反复取得新人权益。
5. **教学重复资格。** 目前认定依据已结算局数；未结算重开可重复教学资格，多局先开后结也共享旧计数。体验保护可重复提供，相关权益预算应按账号持久化、预占/核销，不能因未结算或本地清缓存反复领取。
6. **重放一致性缺口。** 教学过渡一次补三排后统一结算，而服务端每个 append 都立即结算。在上述 1,000 个教学样本中，39 个样本在刚完成过渡时，分数或收集量已不一致。例如 seed=387276917，客户端 60 分、8 表情块，服务端重放 90 分、11 表情块。修复前先决定统一的事件语义，并版本化，避免修改协议后拒绝旧局。

上述验证均针对本地当前代码；没有验证线上是否部署相同路径。完整服务端响应摘要见 `security-results.json`。

已有正向基础应保留：服务端发种子、开局扣体力、roundId 幂等、事务入账、持久化完成后返回、客户端未确认奖励不预支。它们不能替代上述授权与协议校验。

## 建议的体验方案

### 以有效玩家操作划分阶段

有效移动、炸弹、道具算玩家操作；无效拖动和自动补排不算。以下边界是第一版待验证方案。

| 玩家操作序号 | 阶段 | 可感知的变化 |
| --- | --- | --- |
| 1–3 | 上手 | 保留真实三步教学，建立填满整行的认知 |
| 4–15 | 连消保护 | 连续 12 次自由操作，每次提供至少一个一格直消解，常见局面尽量提供多个解；轻提示帮助选择 |
| 16–30 | 进阶 | 逐步减少直接答案，出现少量两步规划；阶段内平滑过渡 |
| 31–50 | 挑战 | 更少明显解、更多支撑关系与提前腾挪；保留短暂恢复机会 |
| 51+ | 稳定后期 | 固定出题复杂度、容错与目标压力范围，停止随时长继续加码 |

每局提供简单开场；新账号可有更积极的提示及纠错。账号权益预算不因反复开局而重置。后期稳定不等于无限不死，玩家仍可因决策失误失败；需要用分层策略模拟确认压力不会在恒定出块概率下持续累积。

### 保障局面，而非只改四/五/六格概率

- 为保护段设计有限长度、可验证的小局面模板，通过镜像、块组合和颜色形成变体；提供明确的一格移动后落下补齐的关系。
- 候选生成时模拟完整真实结算：移动、重力、消除、炸弹奖励、自动补排、最低占用行，并检查接下来 2–3 次操作的容易解。仅增加六次随机重试无法构成保底，失败时必须有经过验证的模板或修复构造。
- 规划前几次连续成功之后，仍有容易识别的下一步；同时让不同容易解分支都通过验证，不能只验证一条隐藏唯一解。
- 轻微失误后，按实际棋盘选择尚未展示的后续出排，让玩家重新进入连消；已经展示的预告不偷偷修改。若当前状态不能通过未来出排恢复，要定义明确、有限且可重放的恢复机制，不能声称任何局面都必然有解。
- 注意供给守恒：每次清一行消耗八格，早期每排只补四格，长期每步都消不能只靠一排四格持续供给。需要把有限补排包、支撑块和模板一起设计，并限制单次自动结算链长度，避免爽感变成长时间等待。
- 炸弹要接入连续体验验证：达到 Great 后点奖励炸弹，如果后续没有满行会断连。可以优先设计点炸弹后仍有后续满行机会；若决定让爆破直接维持连击，则需要明确修改计分定义并同步双端，不能只改文案。

### 用真实变化表现梯度

阶段显示用“轻松热身 → 连消时刻 → 进阶挑战 → 大师挑战”等产品语言；只在切换时短提示，提前告诉玩家接下来要多想一步。配合轻量音效/背景/连击反馈，并真实减少直接解、增加规划深度。避免频繁弹窗，也不要用顶部濒死状态代替难度说明。

现有提示实际为两秒触发，但轮播文案仍写八秒，可顺手统一。主要问题仍是棋盘是否有解，提示频率只是辅助。

### 连续爽感和可兑现奖励分别治理

分数、爆消表现、非兑现的本局成长可以充足；可兑现开心豆只来自服务端确认的有效收集和明确预算。新手保护不能带来无限可兑现奖励。不要用提高换豆门槛代替风控，也不建议临近奖励阈值突然加难或压低表情出现率。

建议每账号使用服务端持久化的日权益预算、新人权益预算及唯一奖励流水；相同账号的并行局共同占用预算，同一 roundId 永不重复入账。具体每日额度需要结合单豆成本、正常玩家产出分位数和业务预算确定，本次没有足够数据给出合理绝对值。预算状态应有清楚且不打断操作的展示。

可兑现模式的关键进度应分段提交并持久化权威操作序号与状态，逐段核验；未来未展示的补排种子可分段签发，降低整局离线预计算的便利性。服务端时间、操作节奏、账户并发和异常轨迹只作为组合信号，不能仅凭速度或重复步骤认定作弊。遵守规则的机器人仍可能通过重放，因此账号和兑现额度是经济损失的硬边界；离线模式可继续玩，权益需在线确认且受同一预算约束。

所有开局绑定 rulesVersion、difficultyVersion、seed/分段种子、玩家类型及奖励政策；双端按照开局版本计算，在途对局不得被热更新改变规则。中期应将两份独立引擎的纯规则提取为可共用实现，避免再次出现教学事件顺序差异。

服务端维护权威规则、验证道具消耗及状态变化也是官方后端文档建议的基本做法，见 [Unity Cheat prevention](https://docs.unity.com/en-us/cloud-code/3.0.0/cheat-prevention) 与 [Game state management](https://docs.unity.com/en-us/cloud-code/3.0.0/game-state-management)。本文阶段边界和体验指标是针对本游戏的建议，不是引用这些文档的数值结论。

## 验证与交付次序

先修结算降级、空重放、道具授权及教学重放一致性，再做 15 操作友好开场与有解验证，再扩展阶段梯度、稳定后期和可视提示。

建议上线门槛：

- 至少 10,000 组种子与模板变体，指定的一格解策略能连续完成保护段 12 次自由操作；验证所有承诺的容易解分支，另测偏离路径后的恢复。不把脚本通过率等同真人体验。
- 保护段能稳定实际演出 Wow/Good/Great/Perfect，至少覆盖第 4、5 次成功，验证炸弹使用和轻微失误。
- 各阶段统计一步解覆盖率、容易解占合法移动的比例、移动距离、两步可解率、连续无消除次数、棋盘最高点、连击长度和每分钟收集量；按随机、提示、两步规划和更强策略分别模拟。
- 51 次操作之后继续跑 100/200/500 次策略样本，检查后期条件化压力分布；死亡率随生存时间变化需要解释，不能仅比较幸存者的平均高度。
- 真正新玩家验证前 15 次操作内的连击、操作耗时、求助次数、失败点、首局完成和再开局；建议将多数新人能见到 Perfect 作为首要目标，具体目标经过小流量基线确定。
- 安全回归覆盖 legacy 新局、零收集造分、未授权救场、伪造库存、任意 append、重复/并发结算、反复重开、访客切换、预算并发占用及规则更新后的在途局。

本轮已有验证：客户端数据模块 27/27 测试、服务端 API 13/13 测试通过；这些测试目前未覆盖上述关键安全缺口及教学批量补排差异，通过不代表风险已经修复。
