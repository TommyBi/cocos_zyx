## 4. 发布顺序与每步完成条件

### 第一步：固定本次候选，准备环境回退

确认使用随包指纹对应的源与包。若源码又有改动，需要另建候选、重新测试构建，不能直接上传已失配的旧包。保留旧微信ZIP及旧运行镜像；记录每个环境的容器、镜像ID、源指纹和业务数据摘要。

每个环境切换前只对目标游戏服务做一致性SQLite备份（必要时短暂停止该目标服务）；记录备份路径、哈希及可读性，并保存旧镜像与受保护的原配置。测试和正式数据卷分别处理；不在聊天或包内保存`.env`或玩家资料。发布中只动这两个选定的游戏服务，现有共享网关路由不变，无需重启/重载Caddy。

### 第二步：先部署测试API9

将归档中的完整`server/`候选放到已核对的目标目录；同步前先dry-run，排除`node_modules/`、`data/`、`.env*`，保留现有密钥、配置与数据。不用服务器旧文件回填候选。当前两环境共用源码目录：源码更新后，Production在容器切换前仍运行旧镜像，必须分别记录源码与运行状态。

在服务器目标目录构建并仅切换测试服务：

```sh
docker compose -f docker-compose.staging.yml build cocos_zyx_api_staging
docker compose -f docker-compose.staging.yml up -d --no-deps --no-build cocos_zyx_api_staging
```

切换完成后，从实际测试容器读取四个运行文件及锁文件哈希，与候选比较；确认HTTPS返回API9/结构8/气球能力。随后在本地完整候选根目录运行：

```sh
node scripts/check-cloud.js staging
```

它会创建独立零分测试档案，验证V5/V6开局与结算、体力幂等/耗尽、每日分享、商城余额不足、排行榜及退役路由；不使用真实玩家账号。必须完成协议与实际代码核对，健康接口200只能证明服务响应。

### 第三步：上传开发版/体验版并做微信真机验收

导入`build/wechatgame`，确认正式AppID、竖屏、基础库和合法域名。按现有配置核对Staging/Production的request域名、CDN的downloadFile域名，以及现有头像下载域名。不开“跳过域名校验”来掩盖缺失配置。使用真机扫码，至少验证：

- 老账号资产、体力、库存及最高分保留；新手/普通开局、移动、消行、三连炸弹和V6涨行。
- 首页、排行榜、授权复用、商城兑换、分享领取、结算到账及重复结算不多发。
- 气球出现阈值/60秒间隔、拒绝与取消、分享返回、四分之一清除、200ms同步爆炸、输入恢复；首次复活8排、第二次失败结算。
- 首页曲、入局切曲、暂停/继续、结算、回首页、声音开关/音量、切后台/锁屏/恢复。**先定位本地首页无声反馈，再在微信真机确认目标行为；未确认前不能宣称声音验收通过。**
- 慢网与特效分包失败时仍能开始和文字反馈；音乐/分享图确实从CDN下载；小屏、平板及安全区无关键遮挡。

上传时显式填写本次版本号和更新说明。现有上传脚本的默认`1.3.0-*`及“首发/周榜”备注不应直接沿用；本轮没有擅自选定上传版本号。可使用：

```sh
node scripts/upload-wechat.js <确认后的版本号> "V6棋盘、气球救场、排行授权、音乐控制与分包优化"
```

### 第四步：部署正式API9，回归旧客户端

测试及真机验收通过后，再对Production完成目标服务备份，使用同一份候选构建并切换：

```sh
docker compose -f docker-compose.yml build cocos_zyx_api
docker compose -f docker-compose.yml up -d --no-deps --no-build cocos_zyx_api
```

核对实际容器代码与候选哈希、正式API9能力、现有数据摘要，再运行：

```sh
node scripts/check-cloud.js production
```

确认`/debug/profile`及`/debug/reset`均404，保留生产调试隔离；检查旧V5客户端仍可新开局、结算、查询原最高分与余额，新V6客户端同样可用。确认Dawn健康与既有服务未受影响。这里不执行任何玩家重置。

### 第五步：提交审核，审核后发布微信客户端

两个API环境均为API9、真机验收完成、上传版本号与本包指纹一致后，用户在微信公众平台核对审核信息并提交。审核通过后按计划发布客户端，再观察新老版本开局、结算错误、到账、排行榜、CDN和声音。V5/V6并行兼容需持续覆盖旧客户端和在途局，不能仅因审核通过就立刻移除。

## 5. 放行条件与回退

本轮已执行的构建、自动化、HTTP与CDN检查见`release-info.json`；线上部署和真机验证仍须按上面流程执行。当前阻止直接宣称“可提审”的条件是：两个在线API尚未升级，以及音乐等微信真机验收未完成。首页无声反馈必须有定位结论或明确的真机证据，不能由自动化通过推断其不存在。

客户端出现问题时优先停止推广新客户端或回到已验收V5客户端，后端保留支持V5/V6的API9，使新产生的V6在途局仍能结算。**一旦API9接收过V6开局，不能直接把后端降为API8：API8无法重放V6。** 应优先修复API9，或使用另行验证过仍支持V6的回退镜像。只有确认没有V6对局及新增相关写入时，才可评估回到旧API8镜像。

代码回退不自动回滚数据库；禁止用发布前数据库覆盖发布后的玩家进度。CDN旧哈希资源继续保留，避免已发客户端或在途页面找不到资源。不要运行全平台`docker compose down -v`、镜像/卷清理或共享网关重启。

发布负责人最终记录：上传版本号、审核/发布状态、两个实际镜像ID、四文件运行指纹、备份位置、协议与真机结果、数据保留摘要、未解决问题及回退决策。本轮准备工作不会代替这些上线证据。
